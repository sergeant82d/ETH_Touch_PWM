# Firmware audit, 2026-10-06

Requested: a deep audit of SPI bus sharing, network failover, SD card robustness, MQTT and
loop health. Scope: everything in `src/` and `include/` at commit `b13c655`, all three
builds. Every claim was checked against the code that actually runs: Arduino-ESP32 core
3.3.11 and PubSubClient 2.8 (in `~/.platformio`), plus the bench board's event log
(6U_Rack_Fans, COM15, 192.168.10.223), read on the day.

No code was changed. The code blocks are sketches against this code base: not compiled and
UNTESTED on a board. Line numbers refer to `b13c655`.

## The prompt's assumptions vs. this code

| Assumed | Actual |
|---|---|
| W5500 and SD card share one SPI bus | Never. The W5500 has SPI2 to itself on every build. The SD card is on SPI3: shared with the LCD on both Touch-LCD-2 builds, alone on the ESP32-S3-ETH. |
| EthernetClient and WiFiClient must be swapped on failover | One TCP/IP stack (lwIP) and one `NetworkClient`; the stack picks the interface. What matters is when MQTT reconnects (2.1). |
| Change events are logged asynchronously | Every event is written from the main loop task. The only interrupt handlers count tach pulses. |
| `while (!client.connected())` loops | None. One connect attempt per 15 s; the long waits are inside the libraries (4.1). |

## 1. SPI bus sharing (W5500 and SD card)

**Verified sound.** No W5500/SD collision is possible on any build.

- **W5500:** the core's global `SPI` object (`SPIClass SPI(FSPI)`, the S3's SPI2), started on
  the W5500 pins and handed to the core ETH driver (`fan_network.cpp:454-456`). The driver
  wraps every W5500 access in `SPI.beginTransaction()` (a FreeRTOS mutex per SPI object) and
  drives chip select itself, at 20 MHz (core `ETH.cpp:500-573`). This runs in the W5500
  receive task and the lwIP task, not in `loop()`; the mutex keeps those two apart.
- **SD card:** an `SPIClass(HSPI)` object, the S3's SPI3. On the Touch-LCD-2 builds it is the
  LCD's object (`display.cpp:32-33`, started with the SD's MISO at `:491`;
  `sd_logger.cpp:469`); on the ESP32-S3-ETH a separate object on its own pins
  (`sd_logger.cpp:471-479`). The core SD driver takes the bus lock around every card command
  (core `sd_diskio.cpp:446-460`).
- **The right SD library is built.** `.pio/build/*/lib66e/SD/` holds the core's
  `sd_diskio.cpp.o`. The generic Arduino SD 1.3.0 that the ST7789 library pulls into
  `.pio/libdeps/*/SD` is not compiled. That library would have run the card on the global
  `SPI` object, the W5500's bus. The `SD=symlink://...` line in `platformio.ini` is what
  prevents it: keep it.
- **One task on SPI3.** LCD drawing and all SD access run on the loop task. All 39
  `sdLogEvent()` calls are made from loop context (touch handler, network step, the MQTT
  callback inside `mqtt.loop()`, web handlers). The network-event callback, which runs in
  another task, deliberately doesn't log (`fan_network.cpp:319-322`).
- **Dropping a bad card leaves the LCD alone.** `SD.end()` doesn't stop the SPI bus
  (core `sd_diskio.cpp:739-757`).

### 1.1 Low (rule): the bus lock is not recursive

**Where:** core `SPI.cpp:29-31, 199-216`; any future code that draws on the LCD or touches
the SD card.

**Risk:** `beginTransaction()` takes a plain mutex and waits forever. If SD code runs while
the LCD holds an open transaction on the same bus, from the same task (for example
`sdLogEvent()` between an Adafruit `startWrite()` and `endWrite()`), the loop task waits on
itself. The watchdog restarts the board 30 s later and names whatever stage was running. No
code does this today (`display.cpp` has no `startWrite()` blocks); it is a rule for later
edits.

```cpp
// Never: SD access while an LCD transaction is open (same bus, same task: hangs)
screenMain.startWrite();
sdLogEvent("DISPLAY", "...");   // SD waits for the bus lock the LCD holds
screenMain.endWrite();
// Instead: finish drawing, then log.
```

### 1.2 Low, hypothesis: W5500 Lite SPI clock

**Where:** `fan_network.cpp:456`. `ETH.begin()` is called without a clock, so the W5500 runs
at the core default of 20 MHz (core `ETH.h:127, 181`).

**Risk:** on the W5500 Lite build the module hangs off header pins on jumper wires. The
W5500's SPI has no checksum, so a marginal signal gives silently wrong register reads, which
the driver can take for a link or receive problem. All three "Ethernet without an address"
cases so far (COM9 twice on 2026-09-29, COM15 on 2026-10-06) were on this build. The
ESP32-S3-ETH, with its W5500 on the board, hasn't shown it, but it has run this firmware far
less. That proves nothing; a slower clock is a cheap test.

```cpp
// fan_network.cpp, networkInit(): the last argument is the SPI clock in MHz
#if defined(BOARD_LCD2_LITE)
static const uint8_t W5500_SPI_MHZ = 10;   // jumper-wired module: half speed while testing
#else
static const uint8_t W5500_SPI_MHZ = 20;   // core default
#endif
ethPresent = ETH.begin(ETH_PHY_W5500, 1, W5500_CS, W5500_INT, W5500_RST, SPI, W5500_SPI_MHZ);
```

10 MHz still moves about 1 MB/s, far more than this firmware needs.

## 2. Network failover (Ethernet, WiFi, hotspot)

**Verified sound.** `networkLoop()` (`fan_network.cpp:313-387`) is a flat state machine run
every 500 ms: three flags (`staActive`, `apActive`, `scanning`) and a few timestamps, no
nested if/else trees, every timer overflow-safe. Hysteresis is built in: WiFi after 30 s
without Ethernet and off 60 s after it's back; hotspot after 60 s without any network (held
while a WiFi join is within 45 s) and off 30 s after a network returns. Watching the state
from the loop, instead of acting in the network-event callback, is right: that callback runs
in another task. With only the hotspot up, MQTT stops trying (the hotspot doesn't count as a
network, `mqtt.cpp:483-486`), the web page answers on 192.168.4.1, and logging carries on.

### 2.1 Medium, confirmed: MQTT moves to Ethernet too early and drops again

**Where:** `fan_network.cpp:371-386` (`mqttReconfigure()` on every switch away from Ethernet or
WiFi) and `stopSta()`, `:218-224`.

**Risk:** when the cable comes back, `activeNetwork()` says "Ethernet" as soon as Ethernet has
an address, and MQTT reconnects at once. WiFi stays joined for another 60 s. Both interfaces
are on 192.168.10.0/24 (WiFi .222, Ethernet .223), and lwIP keeps sending the new connection
over WiFi. When WiFi is switched off 60 s later, that connection dies and MQTT reconnects a
second time: two drops in HA instead of one. The event log says "over Ethernet" both times,
because it prints the preferred network, not the route in use. From the bench board on
2026-10-06:

```
08:40:29 NET  in use: Ethernet
08:40:29 MQTT disconnected: settings or network changed
08:40:30 MQTT connected to 192.168.10.85 over Ethernet      <- actually over WiFi
08:41:29 NET  WiFi backup off: Ethernet is back
08:41:29 MQTT connection lost: connection lost (state -3)
08:41:30 MQTT connected to 192.168.10.85 over Ethernet
```

**Fix:** keep MQTT on WiFi through the 60 s check, move it once when WiFi goes, and log the
address the connection really uses.

```cpp
// fan_network.cpp, networkLoop(), network switch
if (lastActive[0]) {
    sdLoggerMarkStage("net:dns");
    restoreDnsAndTime("network switch");
    // Away from Ethernet: the connection may have used the cable, reconnect now.
    // WiFi -> Ethernet: WiFi stays up 60 s more and keeps carrying the connection;
    // stopSta() reconnects when WiFi really goes. (WiFi -> none: mqttLoop() handles it.)
    if (strcmp(lastActive, "Ethernet") == 0) mqttReconfigure();
}

// fan_network.cpp, stopSta(), after applyWifiMode()
mqttReconfigure();   // the MQTT connection may have been running over WiFi

// mqtt.cpp, tryConnect(): log the interface address actually used
sdLogEvent("MQTT", String("connected to ") + config.mqttBroker + " from " +
                   net.localIP().toString() + " (" + activeNetwork() + ")");
```

**Check on the board:** cable out, wait for WiFi, cable in. The event log should show one
"connected ... from 192.168.10.223" right after "WiFi backup off", and no "connection lost".

### 2.2 High: Ethernet link without an address is never retried

**Where:** `networkLoop()`, `fan_network.cpp:341-369`. "Up" needs link and address (`:341`),
which is right, but nothing acts on "link up, no address".

**Risk:** if DHCP doesn't finish after a link drop (open item: COM9 on 2026-09-29, COM15 on
2026-10-06 with 73 min off MQTT), the board falls back to WiFi if one is set, else the
hotspot, and never retries Ethernet. The only way back is a restart, now the general
15-minute self-heal.

**Fix:** the step `docs/TODO.md` already plans, made specific: restart the DHCP client after
20 s; if that doesn't help, restart the board, backing off in case the DHCP server itself is
down. Rebuilding the interface in place (`ETH.end()` then `ETH.begin()`) is not recommended:
mDNS keeps a pointer to the interface, the same trap as the hotspot crash of 2026-10-04.

```cpp
// fan_network.cpp (add #include <LittleFS.h>); call from networkLoop() right after `bool ethUp = ...`
RTC_NOINIT_ATTR static uint32_t ethHealMagic;
RTC_NOINIT_ATTR static uint32_t ethHealCount;    // restarts in a row for this reason

static void ethNoAddressCheck(unsigned long now) {
    static unsigned long since = 0;               // 0 = not in this state
    static bool dhcpRestarted = false;
    if (ethHealMagic != 0xE7A0DD01) { ethHealMagic = 0xE7A0DD01; ethHealCount = 0; }  // power-up
    if (ETH.hasIP()) ethHealCount = 0;            // Ethernet worked: start over next time
    if (!config.ethDhcp || !isEthernetConnected() || ETH.hasIP()) { since = 0; dhcpRestarted = false; return; }
    if (since == 0) { since = now; return; }

    if (!dhcpRestarted && now - since >= 20000) {
        dhcpRestarted = true;
        sdLoggerMarkStage("net:dhcp");
        esp_netif_dhcpc_stop(ETH.netif());
        esp_err_t e = esp_netif_dhcpc_start(ETH.netif());
        sdLogEvent("NET", String("Ethernet link up, no address for 20 s: DHCP restarted (") + esp_err_to_name(e) + ")");
    }
    // Then a restart: 3 min, 6, 12 ... up to ~3 h; not while the WiFi backup carries the traffic
    unsigned long limit = 180000UL << min(ethHealCount, (uint32_t)6);
    if (now - since >= limit && !isWifiConnected()) {
        ethHealCount++;
        sdLogEvent("RESTART", "source=self-heal Ethernet link up without an address (" + String(ethHealCount) + " in a row)");
        delay(500);
        LittleFS.end();
        delay(200);
        ESP.restart();
    }
}
```

If the item comes back, the NET events show which step fixed it.

### 2.3 Medium: self-heal restarts every 15 minutes in any MQTT outage

**Where:** `selfHealCheck()`, `mqtt.cpp:456-469`.

**Risk:** it fires whenever MQTT is set up but not connected for 15 min, whatever the cause:
router down, HA or Mosquitto down for maintenance, or the board on its setup hotspot. In each
case the board restarts every 15 min until the outage ends. Each restart drops a phone on the
hotspot, runs the fans at full speed for the first second or two (no probe reading yet), and
wipes the day's hi/lo values (3.6). It was meant for the board's own stuck state, which 2.2 handles directly.

**Fix:** back off after each self-heal restart, and leave the hotspot alone while someone is on
it. The count lives in RTC memory, so it survives the restart it causes.

```cpp
// mqtt.cpp (add #include <WiFi.h>)
RTC_NOINIT_ATTR static uint32_t healMagic;
RTC_NOINIT_ATTR static uint32_t healCount;       // self-heal restarts in a row

static void selfHealCheck() {
    static unsigned long okSinceMs = 0;
    if (healMagic != 0x5E1F4EA1) { healMagic = 0x5E1F4EA1; healCount = 0; }   // power-up
    if (!mqttWanted() || mqtt.connected()) { okSinceMs = millis(); healCount = 0; return; }
    if (isHotspotActive() && WiFi.softAPgetStationNum() > 0) { okSinceMs = millis(); return; }
    unsigned long limit = SELF_HEAL_MS << min(healCount, (uint32_t)4);   // 15, 30, 60, 120, 240 min
    if (millis() - okSinceMs < limit) return;
    healCount++;
    // ... log (add healCount to the reason) and restart as now ...
}
```

### 2.4 Low: SD writes are blamed on the step that asked for them

**Where:** `appendLine()`, `sd_logger.cpp:189-206`; stage names in `main.cpp:136-221`.

**Risk:** `sdLogEvent()` doesn't set a stage of its own, so a slow SD write made from the
network, MQTT, web or touch step shows up in a watchdog BOOT event as `stage=network` (and so
on). Since commit `c3f1121` the network step writes NET events itself.

**Fix:** mark SD writes as their own stage, then put the caller's back.

```cpp
// sd_logger.cpp: rename the current appendLine() to appendLineImpl(), then
static void appendLine(const char* sdPath, const String &line) {
    char caller[sizeof(rtcSnapshot.stage)];
    memcpy(caller, rtcSnapshot.stage, sizeof(caller));
    sdLoggerMarkStage("sd:write");
    appendLineImpl(sdPath, line);
    sdLoggerMarkStage(caller);
}
```

**About the 03:16 watchdog restart (open item).** The firmware running then (started
2026-10-05 20:24; its network code is unchanged from `b91c006`) wrote nothing to the SD card
in the network step. In steady state that step
only read status flags, which can't block (core `NetworkInterface.cpp:316-322, 570-575`). So a
30 s stop there needs one of two things:

- a network change that ran one of the WiFi, hotspot, DNS or time-server calls. These wait on
  the WiFi driver or on the lwIP task; the lwIP waits have no time limit.
- another, higher-priority task that kept the loop from running at all. The stage only says
  where the loop was.

With the current firmware, NET events just before a repeat would point to the first; none
would point to the second.

## 3. SD card robustness and logging

**Verified sound.**

- **No card at boot:** rows go to a 200 KB buffer in internal flash, the card is tried again
  every 15 s, and the buffer is written to it when it's back.
- **Card pulled:** noticed by a raw read of sector 0 every 10 s (`checkCardStillThere()`),
  since file writes can't tell (3.1).
- **Short write windows:** each row opens, appends and closes, which keeps the time a file is
  open (and exposed to a power cut) short. Every file handle is checked before use.
- **Bounded waits:** the core driver limits every wait (500 ms busy waits, 3 tries) and marks
  the card not ready once a command gets no answer, so later calls fail at once (core
  `sd_diskio.cpp:105-209`). A failing card costs seconds, not a hang.
- **No accidental format:** `SD.begin()` is called without formatting, so a bad mount never
  wipes a card.
- **Settings are safe:** LittleFS commits a rewritten file only when it is closed, so a power
  cut during `saveSettings()` (`config.cpp:98-107`) leaves the old settings.

### 3.1 Medium: write errors are invisible

**Where:** `appendLine()`, `sd_logger.cpp:189-206`. The same pattern in `drainSpilloverToSD()`
`:266`, `updateAllTimeRecord()` `:388-392` and `purgeOldDailyRows()` `:428-431`.

**Risk:** the Arduino file layer buffers writes and sends them to the card at `close()`, then
ignores the result of that close (core `vfs_api.cpp:337-349`; `flush()` ignores its results
too, `:395-401`). So `f.print(line); f.close();` counts as success on a card that is gone.
Rows written between the failure and the next card check (up to ~20 s) are lost instead of
going to the buffer.

**Fix:** write through the C file calls, where every step reports failure.

```cpp
// sd_logger.cpp (add #include <stdio.h> and <unistd.h>)
// Writes text to an SD file ("a" = append, "w" = replace). True only if it reached the card.
static bool sdWriteChecked(const char* path, const char* mode, const String &text) {
    char full[64];
    snprintf(full, sizeof(full), "/sd%s", path);   // SD.begin() mounts the card at /sd
    FILE* fp = fopen(full, mode);
    if (!fp) return false;
    bool ok = fwrite(text.c_str(), 1, text.length(), fp) == text.length();
    ok = fflush(fp) == 0 && ok;               // C buffer -> FAT layer
    ok = fsync(fileno(fp)) == 0 && ok;        // FAT layer -> card
    ok = fclose(fp) == 0 && ok;
    return ok;
}

static void markCardMissing() { SD.end(); sdPresent = false; usedPercent = -1; }

static void appendLine(const char* sdPath, const String &line) {
    if (sdHasFreeSpace()) {
        String header = SD.exists(sdPath) ? String() : csvHeaderFor(sdPath);  // new file: column names
        if (sdWriteChecked(sdPath, "a", header.length() ? header + "\n" + line : line)) return;
        Serial.println("WARNING: SD write failed - card marked missing, spilling to internal flash.");
        markCardMissing();
    }
    appendToSpillover(sdPath, line);
}
```

### 3.2 High: the buffer drain can lose everything it holds

**Where:** `drainSpilloverToSD()`, `sd_logger.cpp:241-273`, called right after a remount
(`:615`).

**Risk:** lines are written with `if (out) out.print(...)`. A failed open skips lines silently,
write errors aren't seen (3.1), and the buffer file is deleted regardless (`:270`). A card that
comes back flaky, just when a drain runs, loses everything buffered while it was out: up to
200 KB, about two days of rows. If the 2026-10-04 note "some cards were lost once the
buffered data was written to them" means logged data went missing, this path would explain
it. The drain also writes the whole buffer in one call
inside the loop, so fans, LCD, web and MQTT wait for it.

**Fix:** drain in slices from the loop, remember the position, and delete the buffer only when
everything is confirmed. Lines for one file are still written together.

```cpp
// sd_logger.cpp: replaces drainSpilloverToSD(). Call every sdLoggerLoop() pass, after the
// clock check. Set spillPending in appendToSpillover() and in sdLoggerInit() if the file exists.
static bool spillPending = false;
static size_t drainPos = 0;                          // bytes of the buffer already on the card

static void drainSpilloverSlice() {
    if (!spillPending || !sdPresent || !isLittleFsMounted()) return;
    File f = LittleFS.open(SPILLOVER_PATH, FILE_READ);
    if (!f) { spillPending = false; return; }
    size_t size = f.size();
    f.seek(drainPos);
    String monthPath = "/logs/" + String(year()) + "-" + (month() < 10 ? "0" : "") + String(month()) + ".csv";
    String runPath, run;                             // consecutive lines for one file
    size_t runEnd = drainPos;
    while (f.position() < size && run.length() < 2048) {
        String line = f.readStringUntil('\n');
        String path = monthPath;                     // lines from before 2026-09-28 have no path
        int tab = line.indexOf('\t');
        if (tab > 0) { path = line.substring(0, tab); line = line.substring(tab + 1); }
        if (run.length() && path != runPath) break;  // next file: next call (runEnd not moved)
        runPath = path;
        if (line.length()) { run += line; run += '\n'; }
        runEnd = f.position();
    }
    f.close();
    if (run.length()) {
        String header = SD.exists(runPath) ? String() : csvHeaderFor(runPath);
        if (!sdWriteChecked(runPath.c_str(), "a", header.length() ? header + "\n" + run : run)) {
            markCardMissing();                       // drainPos unchanged: retried after the remount
            return;
        }
    }
    drainPos = runEnd;
    if (drainPos >= size) {                          // all of it is on the card
        LittleFS.remove(SPILLOVER_PATH);
        drainPos = 0;
        spillPending = false;
        spilloverCapWarned = false;
    }
}
```

`drainPos` is lost on a restart, so a restart in mid-drain writes some lines twice; that beats
losing them. With the drain in slices, the 200 KB cap could also be raised (LittleFS has
about 9 MB), giving weeks without a card instead of about two days.

### 3.3 Medium: delete-then-write of the all-time record and the rollups

**Where:** `updateAllTimeRecord()`, `sd_logger.cpp:382-393` (parsing at `:337-366`);
`purgeOldDailyRows()`, `:423-435`.

**Risk:** both files are removed, then written again. A power cut, reset or card fault between
the two loses the all-time record, or all 30 days of rollups. Separately, if `alltime.csv`
has no `ALL,` row (cut short), `line` still holds the last line read, usually the column
names. Every value then parses as 0, and zeros are written as the new record. The comments at
`:383-386` and `:424-426` are also wrong for this core: `FILE_WRITE` is `"w"`, which truncates
(core `FS.h:30`).

**Fix:** write a temporary file, check it, then swap; finish an interrupted swap at boot;
ignore a file without its `ALL,` row.

```cpp
// sd_logger.cpp: replaces "SD.remove(path); SD.open(path, FILE_WRITE); print; close"
static String tmpPathFor(const char* path) { String t = path; t.replace(".csv", ".tmp"); return t; }

static bool sdReplaceFile(const char* path, const String &content) {
    String tmp = tmpPathFor(path);
    SD.remove(tmp);
    if (!sdWriteChecked(tmp.c_str(), "w", content)) { SD.remove(tmp); return false; }
    SD.remove(path);                    // FAT rename won't overwrite
    return SD.rename(tmp, path);        // power cut here: sdRecoverReplace() finishes it
}

// sdLoggerInit() and after each remount, for both files
static void sdRecoverReplace(const char* path) {
    String tmp = tmpPathFor(path);
    if (SD.exists(tmp) && !SD.exists(path)) SD.rename(tmp, path);  // tmp was complete
    else SD.remove(tmp);                                           // swap never started
}

// updateAllTimeRecord(), right after the read loop:
if (!line.startsWith("ALL,")) line = "";   // no record row: don't parse column names as 0
```

### 3.4 Medium: with no card, every retry freezes the loop

**Where:** `sdLoggerLoop()`, `sd_logger.cpp:605-617`.

**Risk** (worked out from the driver code, not measured): with an empty slot, each
`SD.begin()` runs the card start-up. That is two reset commands of up to 3 tries each with
100 ms pauses, then one more reset command when it gives up, plus up to three 500 ms waits if
the card's data line reads low (core `sd_diskio.cpp:140-209, 489-537, 739-757`). Roughly
1-1.5 s, every 15 s, for as long as there's no card. On the Touch-LCD-2 the LCD can't draw
meanwhile (shared bus).

**Fix:** double the interval after each failed try, up to 2 minutes; back to 15 s after a
success. The cost: a card put in after a long absence can take up to 2 minutes to be noticed.

```cpp
// sd_logger.cpp, sdLoggerLoop()
static unsigned long lastSdRetryMs = 0, sdRetryMs = 15000;
if (!sdPresent && millis() - lastSdRetryMs >= sdRetryMs) {
    lastSdRetryMs = millis();
    if (SD.begin(PIN_SD_CS, sdSPI(), 4000000)) {
        sdPresent = true;
        sdRetryMs = 15000;
        // ... mkdir, measure, recover (3.3) as now; the drain (3.2) picks up from here ...
    } else {
        sdRetryMs = min(sdRetryMs * 2, 120000UL);
    }
}
```

The card runs at 4 MHz. The LCD already drives the same clock and data lines faster than that,
so 16 MHz is worth a try (`SD.begin(PIN_SD_CS, sdSPI(), 16000000)` in both places). It would
cut the time of every SD write, drain and download about four times. Go back to 4 MHz if a
card misbehaves.

### 3.5 Low: nothing is logged until the clock is set

**Where:** `sdLoggerLoop()`, `sd_logger.cpp:568`.

**Risk:** after a power cut with the network down (no time server), no minute rows are written
anywhere while the fans run. After a restart the clock survives, so this is only the
power-cut case, which is also when a record matters most.

**Fix:** hold the rows in RAM with their uptime and write them, back-dated, once the clock is
set. 30 rows (half an hour) cost about 2 KB.

```cpp
// sd_logger.cpp: lastMinuteLogMs moves to file scope; the row text after the timestamp
// comes from one function, rowFields(), used by both paths
struct EarlyRow { uint32_t upS; char fields[48]; };
static EarlyRow early[30];
static int earlyCount = 0;

// sdLoggerLoop(), in place of `if (timeStatus() == timeNotSet) return;`
if (timeStatus() == timeNotSet) {
    if (millis() - lastMinuteLogMs >= 60000 && earlyCount < 30) {
        lastMinuteLogMs = millis();
        early[earlyCount].upS = millis() / 1000;
        strlcpy(early[earlyCount].fields, rowFields().c_str(), sizeof(early[0].fields));
        earlyCount++;
    }
    return;
}
for (int i = 0; i < earlyCount; i++) {            // clock just set: write them back-dated
    time_t t = now() - (millis() / 1000 - early[i].upS);
    char ts[24], path[24];
    snprintf(ts, sizeof(ts), "%04d-%02d-%02d %02d:%02d:%02d", year(t), month(t), day(t), hour(t), minute(t), second(t));
    snprintf(path, sizeof(path), "/logs/%04d-%02d.csv", year(t), month(t));
    appendLine(path, String(ts) + "," + early[i].fields);
}
earlyCount = 0;
```

### 3.6 Medium: the day's hi/lo values live only in RAM

**Where:** `static DailyExtremes today`, `sd_logger.cpp:287`, reset at every boot (`:500`); day
change at `:596-603`.

**Risk:** any restart (OTA, settings, watchdog, self-heal) starts the day's min/max over, so
the "Summary of the day" on the card and in HA covers only the time since the last restart.
A restart across midnight skips that day's rollup row entirely (`lastLoggedDay` starts at -1,
`:597-598`).

**Fix:** keep them in RTC memory, like the state snapshot.

```cpp
// sd_logger.cpp. Change DAILY_MAGIC whenever DailyExtremes changes (as SNAPSHOT_MAGIC).
RTC_NOINIT_ATTR static DailyExtremes today;      // was: static DailyExtremes today;
RTC_NOINIT_ATTR static int rtcLoggedDay;         // the day `today` belongs to
RTC_NOINIT_ATTR static uint32_t rtcDailyMagic;
static const uint32_t DAILY_MAGIC = 0xDA11E0E0;

// sdLoggerInit(): in place of resetDailyExtremes()
if (esp_reset_reason() == ESP_RST_POWERON || rtcDailyMagic != DAILY_MAGIC) {
    resetDailyExtremes();
    rtcLoggedDay = -1;
    rtcDailyMagic = DAILY_MAGIC;
}
lastLoggedDay = rtcLoggedDay;      // a restart over midnight now still closes the old day

// sdLoggerLoop(): wherever lastLoggedDay is set, also
rtcLoggedDay = lastLoggedDay;
```

## 4. MQTT

**Verified sound.** One `NetworkClient` on the shared lwIP stack (`mqtt.cpp:23-24`) works over
Ethernet and WiFi alike, so there is nothing to re-bind; the question is only when to
reconnect (2.1). There are no polling loops: one attempt per 15 s (`:495-503`), TCP connect
capped at 2 s (`:448`), discovery re-sent only when it changed (`:423-427`), no attempts while
only the hotspot is up, and the 30 s loop watchdog behind it all. The broker is set by IP
address (192.168.10.85), so there is no DNS lookup per attempt.

### 4.1 Medium: long waits inside the MQTT library

**Where:** `tryConnect()` calls PubSubClient `connect()` (`PubSubClient.cpp:257-264`); every
`mqtt.publish()` ends in core `NetworkClient::write()` (`NetworkClient.cpp:386-445`).

**Risk:**

- After the TCP connect, PubSubClient waits for the broker's reply in a tight loop, without
  yielding, up to the socket timeout (5 s, `mqtt.cpp:447`). A broker that accepts the
  connection but answers slowly (busy, restarting, still checking the login) freezes the loop
  up to ~7 s per attempt, every 15 s.
- When the other end stops acknowledging without closing the connection (broker host gone,
  path broken), each write waits up to 10 × 1 s for buffer space, then returns short. The
  client still counts as connected, so the next publish waits again. `publishState()` sends
  several messages per pass, and three such waits reach the 30 s watchdog. The 15 s
  keep-alive usually drops the connection first, so this needs a burst at the wrong moment
  (HA's birth message triggers about 30 discovery messages).
- A broker set by name would add a blocking DNS lookup to every attempt (core
  `NetworkManager.cpp:47-60`, then `lwip_getaddrinfo`). Keep the IP address.

**Fix:** a shorter reply wait on the LAN, and treat the first failed publish as a dead
connection. Close the socket directly: `mqtt.disconnect()` would try to send a DISCONNECT
packet and wait on the same full buffer.

```cpp
// mqtt.cpp, mqttInit()
mqtt.setSocketTimeout(2);       // a LAN broker answers in milliseconds; caps the reply wait

// mqtt.cpp: use instead of mqtt.publish() everywhere
static bool pub(const String &t, const String &payload, bool retained = true) {
    if (!mqtt.connected()) return false;
    if (mqtt.publish(t.c_str(), payload.c_str(), retained)) return true;
    Serial.println("MQTT: publish failed, closing the connection");
    net.stop();                 // mqtt.connected() is now false: mqttLoop() logs it and reconnects
    return false;
}
```

## 5. Loop health, memory and timers

**Verified sound.**

- **Timers:** every `millis()` timer in `src/` uses the `millis() - start >= interval` form
  (none of the `millis() > deadline` or `start + interval` forms), so the 49.7-day wrap does
  no harm except in 5.3.
- **Heap:** `String` is used throughout (event text, topics, payloads, JSON, HTTP parsing), but
  the strings are short-lived, the ESP-IDF 5 heap allocator handles that pattern well, and
  the firmware already records free heap, its lowest point and the largest free block. The
  2026-10-06 numbers (~252 KB on Ethernet, lows 142-147 KB while on WiFi) show no drift. A
  blanket switch from `String` to `char` arrays would be a lot of churn for no measured gain;
  fix the specific spots below.
- **Tach counters** are read with interrupts off on the core that services them
  (`sensors.cpp:174-177`), which is correct.

**One structural note.** Fan control shares the single `loop()` with web, MQTT, SD and LCD, so
any wait in one of them stalls the fan curve and the failsafe; the PWM hardware holds the last
duty meanwhile. The single loop is also what makes the shared readings and settings safe
without locks, so keep it, and keep each wait bounded (4.1, 3.2, 3.4, 5.1). Moving fan control
into its own task is the bigger alternative; it would need locks around `config` and the
readings.

### 5.1 Medium: a slow web client can hold the loop

**Where:** `readRequest()`, `web_server.cpp:47-76`; `readBody()`, `:78-87`; downloads in
`handleHistoryFile()`, `:1013-1059`, and `handleHistoryDay()`, `:950-974`.

**Risk:**

- Headers are read a line at a time with a 2 s timeout per line, up to 41 lines. There is no
  overall deadline (up to ~80 s) and no length limit per line, so one line can grow a
  `String` until memory runs out. The 30 s watchdog would restart the board.
- Downloads reset the watchdog after every 1 KB chunk, so a phone on a weak link pulling a
  month log (~2.5 MB) keeps the loop busy for as long as it trickles. The broker drops MQTT
  after ~22 s without traffic. A short write (`client.write()` returning less than the chunk)
  is ignored, which corrupts the download.
- `readBody()` spins without yielding for up to 3 s.

**Fix:** one deadline per request, a cap per header line, and a time limit on downloads.

```cpp
// web_server.cpp
static unsigned long reqStart;          // set first thing in handleNativeWebTraffic()

// One line without "\r\n", at most `max` characters; the whole header gets 3 s.
static bool readLine(NetworkClient &c, String &out, size_t max) {
    out = "";
    while (millis() - reqStart < 3000) {
        int ch = c.read();
        if (ch < 0) { delay(1); continue; }   // nothing yet: let other tasks run
        if (ch == '\n') { out.trim(); return true; }
        if (out.length() >= max) return false;
        out += (char)ch;
    }
    return false;
}
// readRequest(): readLine(client, line, 512) for the request line and each header, and
// return false (request dropped) on failure. readBody(): delay(1) when nothing is available.

// Downloads: a time limit instead of feeding the watchdog forever, and no short writes
static const unsigned long DOWNLOAD_LIMIT_MS = 60000;
while (f.available() && millis() - reqStart < DOWNLOAD_LIMIT_MS) {
    int n = f.read(buf, sizeof(buf));
    if (n <= 0 || client.write(buf, n) != (size_t)n) break;
    esp_task_wdt_reset();
}
```

### 5.2 Low: a flash file opened about 8 times a second for one number

**Where:** `isSpilloverNearFull()`, `sd_logger.cpp:231-239`. It is reached through `sdState()`
from the LCD title bar every 200 ms (`display.cpp:434`, via `refreshBarsOnly()` at
`:669-675`), twice a second from `publishState()` (`mqtt.cpp:233-235`), once a second from
`sdLoggerLoop()`, and on every `/api/status`.

**Risk:** each call checks, opens and closes a LittleFS file (flash reads, a file object
allocated and freed) to read a size that only changes when this module writes it. That is
time and heap churn in the busiest path, for nothing.

**Fix:** keep the size in a variable.

```cpp
// sd_logger.cpp
static long spillBytes = -1;            // -1 = not measured since boot

static size_t spillSize() {
    if (spillBytes < 0) {
        spillBytes = 0;
        if (isLittleFsMounted() && LittleFS.exists(SPILLOVER_PATH)) {
            File f = LittleFS.open(SPILLOVER_PATH, FILE_READ);
            if (f) { spillBytes = f.size(); f.close(); }
        }
    }
    return spillBytes;
}
bool isSpilloverNearFull() { return spillSize() > SPILLOVER_MAX_BYTES * 4 / 5; }
// appendToSpillover(): size_t before = spillSize(); at the top, and after a successful
//                      f.print(line): spillBytes = before + line.length();
// drain finished (file removed): spillBytes = 0;
```

### 5.3 Low: uptime wraps after 49.7 days

**Where:** `mqtt.cpp:245` (HA "Uptime"), `web_server.cpp:192`, `sd_logger.cpp:55`
(`uptimeAtReset` in BOOT events).

**Risk:** `millis() / 1000` starts again at 0 after 49.7 days: HA's uptime drops to 0 and BOOT
events show the wrong uptime. This is the only place where the wrap shows.

**Fix:** the 64-bit microsecond timer.

```cpp
#include <esp_timer.h>
static inline uint32_t uptimeSeconds() { return (uint32_t)(esp_timer_get_time() / 1000000ULL); }
```
